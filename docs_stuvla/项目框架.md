# STUVLA 项目框架规划

```text
src/openpi/
├── models/
│   ├── stl/                       # 新增：场景文字定位模块
│   │   ├── locator.py             # LocateAnything 加载与文字定位
│   │   ├── gate.py                # DBNet / 关键帧门控
│   │   └── types.py               # 定位结果的数据结构
│   ├── model.py                   # 修改：统一 observation 定义与预处理
│   ├── pi0_config.py              # 修改：pi05 的 STL/文字 ROI 输入配置
│   └── pi0.py                     # 修改：文字 ROI 视觉信息进入 pi05
├── policies/
│   ├── piper_policy.py            # 修改：Piper 图像与 STL 输入准备
│   ├── policy_config.py           # 修改：创建包含 STL 的完整策略
│   └── policy.py                  # 修改：在线 STL 与动作推理的衔接
├── training/
│   ├── config.py                  # 修改：统一训练和 STL 配置
│   ├── data_loader.py             # 修改：接入定位结果与训练样本
│   └── stl_cache.py               # 按需新增：定位结果的缓存
└── transforms.py                  # 修改：文字 ROI 提取与模型输入构造

scripts/
├── train_piper.py                 # 修改：你的 stuvla 训练入口
├── train.py                       # 按需修改：STL 阶段与训练循环衔接
└── serve_policy.py                # 修改：启动集成 STL 的策略
```

这里的“深度融合”应该落实在以下四个地方。

1. **STL 成为训练管线中的正式阶段。**  
   数据流定义为：`原始图像和指令 → 门控 → 场景文字定位 → 构造文字 ROI → pi05 输入 → 动作损失`。在线定位和读取缓存是这个阶段的两种执行方式，由训练配置选择。

2. **文字 ROI 成为模型的正式输入。**  
   可以直接增加 `text_roi_0_rgb` 和对应有效掩码，同步修改 `Observation` 的相关处理、`inputs_spec()`、图像预处理和 pi05 的视觉输入路径。全局图、腕部图和文字 ROI 经视觉编码后共同参与策略预测。这样文字输入具有明确语义，无需借用左腕相机槽位。

3. **训练和推理共同使用这套实现。**  
   训练时由训练入口管理 STL，推理时由策略构造入口管理 STL；两边调用相同的定位和 ROI 构造逻辑。模型路径、查询方式、门控条件、裁剪规则、设备和缓存模式统一进入现有 `training/config.py` 的配置体系。

4. **模型生命周期也纳入现有流程。**  
   LocateAnything 初始化一次，后续复用。使用当前 JAX 训练路径时，STL 推理放在主进程中、进入 pi05 的 JIT 计算之前，避免在 DataLoader 子进程里重复加载，也避免把 PyTorch 的生成过程放入 JAX 的编译函数。

你原来的 `if iskeyimage:` 可以作为第一阶段接入点；随着融合完善，它会成为上述正式处理流程的一部分，而不是承担所有逻辑的唯一位置。

**代码深度融合与是否联合训练需要分别决定。** 第一版仍可冻结 STL、训练 pi05，但它们在代码、配置和执行管线上已经属于同一个系统。后续如果需要让动作损失影响 STL，再进一步设计可微特征接口和训练目标。
